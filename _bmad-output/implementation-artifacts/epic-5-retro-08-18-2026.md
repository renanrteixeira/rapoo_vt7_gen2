### Fix now

- **F1 — Guided pairing aborts before the user finishes the physical steps.**
  `pairing_session.py:228-233` treats two consecutive `0xA7 data[2]==0` as
  confirmed failure; the device-validated meaning of 0 is "no match in
  progress" (FEATURES.md §E: observed `06 01 00...`), and the receiver replies 0
  while the user is still connecting cable / power-cycling / pressing L+M+R —
  the run FAILS at ~t=4-5 s, making the 60 s window moot.
  _Guard_: grace period before treating consecutive zeros as failure (or
  require ≥N s elapsed / a prior non-zero transient), re-validate the semantics
  on-device via `--pair-run`.
- **F2 — Battery monitor parses the 0xB1 pairing-success report as a battery
  report.** `battery.py:245-258` accepts any rid-7 report with len>8;
  `data[1]==0xB1` → mode 1 (BT icon), garbage DPI → spurious "DPI changed"
  notification. The session's own 0xB1 check is at `pairing_session.py:200-207`.
  _Guard_: skip the pairing sub-command byte in `_handle_report` (e.g. treat
  `data[1]` in {0xB0,0xB1} as non-battery).
- **F3 — Reply cross-talk between monitor and session on the same receiver.**
  `device.py read_response` (first rid-6 ACK, whatever answers) lets the
  session's 0xA7 poll consume a monitor 0xAA ACK (`status=1` → non-zero streak →
  false "pairing success") and lets the monitor consume the session's 0xA7 ACK
  (0% red icon + spurious low-battery). `pairing_session.py:214-219` +
  `battery.py:227-239`.
  _Guard_: filter `read_response` by last-sent cmd_id, or put the monitor in
  listen-only for the session duration (`_listen_quiet` exists).
- **F4 — Stop during the readiness gate still fires the destructive frames.**
  `pairing_session.py:129-144` never checks `self._stop`; a cancel during the
  up-to-6 s gate (or during `_open_receiver`) is ignored and 0xA0/0xA1 fire
  anyway — violating the module's own "never leaves the receiver mid-write"
  guarantee (docstring lines 25-29).
  _Guard_: check `_stop.is_set()` each gate attempt and before `send_command`;
  emit STATUS_CANCELLED.
- **F5 — Destructive ops can interleave on one receiver.** `_pair_busy`,
  `_system_busy`, `_name_busy` are independent (`gui.py:838-850`,
  `_on_factory_reset_clicked`/`_on_rename_clicked`); reset (monitor thread,
  0xAD) + pairing (own thread, 0xA0/0xA1) on the same receiver can collide —
  reset never verifies, RF half-written. No test covers the interleave
  (verification-gap).
  _Guard_: cross-disable the System-tab destructive buttons while any busy flag
  is held; add the cross-guard test.
- **F6 — `encode_name` can raise `UnicodeEncodeError` past the handler.**
  `system.py encode_name` does `str(name).strip().encode('utf-8')`; a lone
  surrogate (pasted clipboard) escapes `_on_rename`'s `DeviceNameError` except →
  uncaught traceback in the GTK signal handler.
  _Guard_: catch `UnicodeEncodeError` → raise a localized `DeviceNameError`.
- **F7 — Stale terminal message survives a new terminal-without-message.**
  `gui.py:879-880` stores `_pair_last_message` only when message is not None;
  a later terminal SUCCESS/FAILED (message None) keeps the previous error string,
  and `_on_lang_changed` re-renders the stale error instead of the correct key.
  _Guard_: clear the stored message on a terminal result without a message.
- **F8 — The 0xB1 burst can be eaten by the 0xA7 poll window.**
  `pairing_session.py:195-219`: the 0.3 s `read_report` listen reads one report,
  then `dev.query`'s 1 s `read_response` discards every rid-7 report in its
  window — the primary (and unvalidated) success signal is the least reliably
  observed.
  _Guard_: flag/return rid-7 0xB1 inside `read_response`, or listen around the
  poll.
- **F9 — `probe.py --pair-run` lacks the readiness gate and leaks OSError.**
  `probe.py pair_run_main` fires start_match/write_rf into a sleeping receiver
  (session protects, harness does not) and an unplug during the send loop shows
  a raw traceback instead of the clean partial result.
  _Guard_: reuse the 3× 0xA7 gate; wrap the send loop in `except OSError`.
- **F10 — `--pair-run`/`--pair-discover` allow write_rf without start_match.**
  `tools/probe.py _pair_destructive` gate permits a plan of only `['write_rf']`,
  which orphans the current mouse with no rollback (rollback is already
  deferred). _Guard_: require start_match whenever write_rf is present.
- **F11 — VID/PID success branch is untested.** `tests/test_pairing_session.py`
  never drives the "none attached at baseline → attached during matching"
  transition (the only test with VID/PID attached sets `a7=0x01` so the 0xA7
  streak already produces success); deleting `pairing_session.py:253-260` leaves
  the suite green.
  _Guard_: session test with a mutable `connected` toggled between baseline and
  matching-loop polls.
- **F12 — Stale protocol docstrings.** `pairing.py:13-15` and `protocol.py:30-32`
  still claim 0xA0/0xA1 are "probe-only / never sent from the app"; the app now
  writes them behind the confirmation dialog. _Guard_: update both to "app write
  path gated by a blocking confirmation dialog; probe-only behind Ask First".

### Defer (tracked)

- **D1 — Monitor-thread language reads expanded.** `_rename_error`/
  `_refresh_name.err` read `LANGS[self._window._lang]` on the monitor thread
  (race on language change), the pre-existing pattern already recorded in
  deferred-work.md for `_factory_reset_error`/`_button_error`/`_param_error`.
  _Lesson_: hop via idle_add before reading `_lang` (match `_rename_done`).
- **D2 — RF rollback after a failed/cancelled pairing.** Already deferred in
  deferred-work.md (no read-RF command mapped); confirmed still absent in
  `pairing_session.py`.
- **D3 — Factory reset `0xAD` never validated live.** FEATURES.md §2 row is ✅
  "implemented", not device-validated; the wipe assertion ships on a command
  whose wire form is only bundle-inferred (the adversarial subagent's
  `[0xAD,0x52,0x3D]` payload claim was NOT found in the bundle and is dropped).
  _Route_: Ask First on-device reset test before trusting the destructive wipe.
- **D4 — `_on_start_pairing` silent return → busy stuck.** `main.py:622-623`; the
  busy flag is only set on a fresh dialog-OK path, so the stuck state is
  theoretical — accept as-is, revisit only if a real trigger appears.

### Accept (recorded so later retros stop re-flagging)

- **A1 — Session owns its own fd + daemon thread** bypassing the submit-queue
  worker pattern — deliberate, documented design (own receiver fd; monitor
  untouched), and the same pattern probe.py uses. The reply cross-talk it risks
  is tracked as F3.
- **A2 — Success-detection semantics shipped unvalidated.** 5-4 ships the GUI
  with 0xB1 / persistent non-zero / VID-PID as candidates, all ⚠️ in FEATURES.md
  §E; 5-3 validated only 0xA7==0 (failure) and the VID/PID read. Documented,
  gated behind the confirmation dialog, pending the Ask First `--pair-run`
  on-device run — a deliberate interpretation of the "no UI before Story 11
  validates" gate (read-only was validated; 0xA0/0xA1 replies are unreadable on
  hidraw). _Lesson_: pin success semantics on-device before shipping the UI.
- **A3 — Size growth: `gui.py` is now 1604 lines / a single `BatteryWindow`
  class** (largest module; pairing block ~+170). Observed, not blocking; the
  render-decision split (`pairing_render_plan` etc.) keeps the growth
  mechanical. Watch for a future split, not now.
- **A4 — Duplication of the awake/readiness probe between the session and
  `probe.py`.** The session has the gate (F4/F9), the harness does not — the
  inconsistency itself is tracked as F9; otherwise `decode_connected_vid_pid`
  and `pairing_commands` are shared, no duplication.
